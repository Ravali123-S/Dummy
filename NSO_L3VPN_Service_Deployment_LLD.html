Step 02

Create Simulated Network — ncs-netsim

ncs-netsim create-network / add-to-network

What This Does

Creates simulated (virtual) routers using netsim — NSO's built-in network simulator. Each simulated device uses a real NED package (cisco-ios-cli-3.0, cisco-iosxr-cli-3.5) so they behave exactly like real routers. Three devices are created: dist-rtr0 (IOS), internet-rtr0 (IOS), and core-rtr0 (IOS-XR).

📌 Why netsim: Allows full NSO testing without physical hardware. Each device gets its own IPC port for communication with NSO tools. NED packages determine which vendor's CLI syntax is simulated.

Commands — Create 3 devices
# Create first IOS device (dist-rtr) ncs-netsim --dir nso-instance/netsim \ create-network \ $NCS_DIR/packages/neds/cisco-ios-cli-3.0 \ 1 dist-rtr # Add second IOS device (internet-rtr) ncs-netsim --dir nso-instance/netsim \ add-to-network \ $NCS_DIR/packages/neds/cisco-ios-cli-3.0 \ 1 internet-rtr # Add IOS-XR core router ncs-netsim --dir nso-instance/netsim \ add-to-network \ $NCS_DIR/packages/neds/cisco-iosxr-cli-3.5 \ 1 core-rtr
Output — Devices Created
Devices Created
dist-rtr0 — Cisco IOS (cisco-ios-cli-3.0)
internet-rtr0 — Cisco IOS (cisco-ios-cli-3.0)
core-rtr0 — Cisco IOS-XR (cisco-iosxr-cli-3.5)
Tool: ncs-netsim Output dir: nso-instance/netsim/ Each device gets: unique IPC port
Step 03

What This Does

Step 04

Push Interface Configuration to netsim Devices — ncs_load via IPC

NCS_IPC_PORT · ncs_load

What This Does

Injects GigabitEthernet interface configuration directly into each simulated device using ncs_load over the device's unique IPC port. This is a raw configuration push — it bypasses NSO's service logic entirely and goes straight to the device's internal config store.

📌 Why needed: netsim devices start with minimal config — no GigabitEthernet interfaces. The L3VPN service template assumes GigabitEthernet interfaces exist. This step creates them before NSO syncs.

IPC = Inter-Process Communication Port
# IOS device (dist-rtr0) — IPC port 5010 NCS_IPC_PORT=5010 ncs_load -Fc -l -m << EOF interface GigabitEthernet5 description A GigE interface no shutdown ip address 192.168.1.10 255.255.255.0 EOF # IOS-XR device (core-rtr0) — IPC port 5012 NCS_IPC_PORT=5012 ncs_load -Fc -l -m << EOF interface GigabitEthernet 0/0/0/1 description A GigE interface ipv4 address 192.168.2.10 255.255.255.0 EOF
Terminal — ncs_load via IPC port
ncs_load Flow
ncs_load command invoked
Uses NCS_IPC_PORT to find device
Connects to netsim device directly
Pushes CLI config (GigabitEthernet)
Device updated ✅ — interface now exists
Tool: ncs_load Transport: IPC (not SSH/NETCONF) Bypass: NSO service logic not involved

Step 05

Login to NSO CLI + Sync-from All Devices

ncs_cli · devices sync-from

What This Does

ncs_cli -C -u admin opens the NSO CLI as admin in Cisco-style mode. Then devices sync-from connects to every registered device, fetches their running configuration, and stores it in NSO's CDB. After this, NSO and all devices share identical configuration state.

📌 Why sync-from: Step 4 pushed config directly to devices, bypassing NSO. NSO's CDB does not know about those changes yet. sync-from reads device reality and updates CDB — making them consistent before any service is deployed.

Step 07

Compile YANG Model → .fxs File

make -B -C packages/l3vpn/src/

What This Does

Runs the NSO YANG compiler (ncsc) to compile l3vpn.yang into l3vpn.fxs. The .fxs file is a compiled binary representation of the YANG model that NSO loads at runtime. Without this compilation step, NSO cannot understand the service schema.

📌 .yang vs .fxs: The .yang file is human-readable source code. The .fxs is NSO's compiled binary format — optimised for fast schema lookup. NSO only reads .fxs files, never .yang directly at runtime.

Compile command
make -B -C packages/l3vpn/src/ # This internally runs: ncsc -c -o ../load-dir/l3vpn.fxs \ yang/l3vpn.yang
Terminal — YANG compilation
Compilation Flow
Source: l3vpn.yang (human-readable)
Compiler: ncsc (NSO YANG compiler)
Output: l3vpn.fxs (binary, in load-dir/)
NSO can now read this schema ✅
Compiler: ncsc (NSO YANG compiler) Input: l3vpn.yang Output: l3vpn.fxs (load-dir/)
Step 08

Login to NSO CLI + Reload All Packages

ncs_cli · packages reload

What This Does

packages reload tells NSO to scan the packages directory, read all compiled .fxs files, and register the new schemas, services, templates, and Python handlers into memory. The L3VPN service becomes live and usable after this step.

📌 What reload does internally: NSO enters a brief upgrade mode → reads all .fxs files → loads service YANG schemas into schema store → registers servicepoints → activates Python handlers → exits upgrade mode. All packages confirmed as result true.

Commands
# Login to NSO CLI ncs_cli -C -u admin # Reload all packages admin@ncs# packages reload # Expected output: reload-result { package cisco-ios-cli-3.0 result true } reload-result { package cisco-iosxr-cli-3.5 result true } reload-result { package l3vpn result true }
Terminal — packages reload output

cisco-iosxr-cli-3.5 → NED for IOS-XR devices
l3vpn → Service package — now active ✅

Step 10

commit dry-run — Preview Config Without Applying

commit dry-run

What This Does

commit dry-run triggers the full NSO FASTMAP pipeline in simulation mode. It generates the exact device configuration that would be pushed — showing VRF, interface, and routing config — but applies nothing to any device. Essential for verification before deployment.

📌 Why dry-run first: Lets engineers review the exact CLI that will be sent to each device, catch errors in the service template, and confirm the diff before committing. Zero risk — no device is touched.

Command
admin@ncs(config)# commit dry-run # NSO runs FASTMAP in simulation mode # Shows what WOULD be sent to devices: native { device { name dist-rtr0 data ip vrf myVPN interface GigabitEthernet5 ip vrf forwarding myVPN ip address 192.168.1.10 255.255.255.0 ip route vrf myVPN 10.0.0.0 255.255.255.0 ... } } # No changes applied to device ❌ (preview only)
dry-run internal flow

FASTMAP computes delta (CREATE)
NED translates → native CLI shown
⚠ Shown to user — NOT sent to device
Config previewed
VRF configuration
Interface configuration (GigabitEthernet)
Static routes (prefix + mask)
Risk: Zero — no device changes FASTMAP: Simulation mode Output: Preview of native device CLI
Service Types — Where Template vs Python Fits in Architecture

Template-based — Mapping via XML template. Simple, fast to develop.

Python-based — Mapping via Python code. Calculations, external integrations.

Python + Template — Python handles logic, Template handles device mapping.

Step 11

commit and-quit — Apply Service to Devices

commit and-quit

What This Does

commit and-quit executes the real deployment: FASTMAP runs in execution mode, generates the device configuration delta, the NED translates it to native CLI, and NSO pushes it to the device over SSH. On success, Candidate CDB is promoted to Running CDB and FASTMAP stores a snapshot for future diff computations.

📌 FASTMAP at work: Only the delta is sent — on first deploy everything is CREATE. On re-run with same inputs, delta is empty → zero commands sent. This is idempotency.

Command + Full Deployment Flow
admin@ncs(config)# commit and-quit # NSO executes real FASTMAP pipeline: # Service CDB → Template → Delta → NED → Device Commit complete. # Service deployed to dist-rtr0 ✅ # Running CDB updated # FASTMAP snapshot stored for next diff
Full FASTMAP Execution Flow
Service data read from Candidate CDB
Template engine generates config subtree
FASTMAP computes delta vs last commit
NED translates YANG delta → native CLI
Config pushed to dist-rtr0 via SSH
Device acknowledges → success
Candidate → Running CDB ✅ Service live 🚀

⚠ Common issue: Syntactically correct config can still be rejected by the device if the physical interface doesn't exist or config conflicts. Use commit | details to troubleshoot.

FASTMAP: Real execution mode Result: Candidate CDB → Running CDB Rollback: Available via rollback file

What This Shows

When input violates the YANG model, NSO rejects it immediately with a precise error pointing to the exact field. Two error types shown: leafref failure (device router1 does not exist in CDB) and type error (IP address 10.300.1.0 is not a valid ipv4-address).

Creates Loopback100 on two devices simultaneously — dist-rtr0 (IOS) and core-rtr0 (IOS-XR). Using commit dry-run outformat xml shows the config as YANG XML — revealing the NED YANG paths used by the template. The IOS-XR device uses different XML namespace (tail-f/ned/cisco-ios-xr) vs IOS.

Deploy to two devices + XML dry-run
admin@ncs(config)# devices device dist-rtr0 \ config interface Loopback 100 admin@ncs(config-if)# ip address 192.168.10.20 \ 255.255.255.255 / top admin@ncs(config)# devices device core-rtr0 \ config interface Loopback 100 admin@ncs(config-if)# ipv4 address 192.168.10.20 \ 255.255.255.255 / top admin@ncs(config)# commit dry-run outformat xml
XML dry-run — NED YANG paths for IOS-XR Loopback

📌 outformat xml shows the YANG XML that NSO will push — using NED YANG namespace. This is exactly what lives in the NED YANG config tree before the NED translates it to CLI. Useful for debugging template variable bindings.

What This Shows

After committing, the deployed config can be viewed in raw XML format using | display xml. This reveals the exact NED YANG XML structure stored in the CDB for core-rtr0's GigabitEthernet interface — showing namespace, element hierarchy, and values exactly as NSO stores them internally.

admin@ncs# show running-config \ devices device core-rtr0 config \ interface GigabitEthernet 0/0/0/1 \ | display xml

📌 Why display xml: The XML format reveals the exact YANG paths and namespaces used. This is critical when developing XML templates — you can see the exact element structure the template must produce.
