Executive Summary — What This Document Covers

When a network engineer types a single command such as simple-service test1 device ios0 bandwidth 100M, Cisco NSO executes a deterministic 22-step pipeline that validates the request, generates device-specific configuration, computes only what has changed, pushes it to the physical device, and commits everything as an atomic transaction — all within seconds.

This document details every step: what triggers it, what it does, and why it is necessary. The flow is divided into 8 phases — from schema registration through final persistence. Two YANG models drive the entire pipeline: the Service YANG (defines what the engineer can ask for) and the NED YANG (defines the device's native configuration vocabulary).

Phase 1
YANG Schema Layer
Before any user request — system startup
Step 01

YANG Model Registration

Both Models

What Happens

When NSO starts or a package is loaded, all YANG model files (simple-service.yang, cisco-ios.yang, huawei-vrp.yang) are compiled and registered into NSO's central schema store. This builds a complete structural map of every valid field, type, and constraint across all services and all device types simultaneously.

📌 Why it matters: This registration happens once at startup. All downstream validation, path resolution, and template rendering consult this in-memory schema — disk files are never re-read during live requests. This makes NSO extremely fast at validation time.

Example

Packages loaded at NSO startup
Package: my-service-pkg
└── simple-service.yang ✓
Package: cisco-ios-ned
└── cisco-ios.yang ✓
Package: huawei-vrp-ned
└── huawei-vrp.yang ✓
All 3 YANG files compiled → schema objects
Registered in NSO schema store (in-memory)
NSO ready to accept requests — no disk reads needed hereafter
Trigger: Package load / NSO startup Output: In-memory schema store populated Failure: Package load rejected — YANG syntax error
Phase 2
Input & Validation
Steps 2 – 5 · User request → staged in CDB
Step 02

User Input — Request Arrives

Service YANG

What Happens

A provisioning request arrives via CLI, RESTCONF API, or NETCONF. NSO accepts this as a candidate configuration edit — a transactional change that has not yet been applied to any device. Nothing is committed or validated yet; this is purely intake.

📌 Why it matters: NSO uses a "candidate then commit" model. By staging first, any failure later in the pipeline can be completely rolled back — no partial configuration ever reaches a real device.

Example

Engineer types in NSO CLI
services simple-service test1
device ios0
bandwidth 100M
Service name = test1
Target device = ios0
Bandwidth = 100M (100 Megabits)
Status: candidate (not yet committed)
Interface: CLI / RESTCONF / NETCONF State: Candidate (uncommitted)
Step 03

NSO Request Processing — Service Type Identified

Service YANG

What Happens

NSO parses the incoming request path (/services/simple-service) and queries the schema store to confirm a YANG model exists for this service type. If the service name is unknown or misspelled, the transaction is rejected immediately with a clear error — no processing occurs.

Example

NSO schema lookup
NSO reads path: /services/simple-service
Schema store: "simple-service" → found ✓
If "wrong-service" → rejected immediately ✗
Lookup target: list simple-service in Service YANG Failure: Unknown service → transaction aborted
Step 04

YANG Validation — 3-Stage Gate

Service YANG

What Happens

NSO runs three sequential validation checks against the Service YANG schema. All three must pass — any failure aborts the transaction with a precise, human-readable error message pointing to the exact field that failed.

Gate 1 — Structure

Are all mandatory fields present? Are there any unknown fields?

device=ios0 ✓
bandwidth=100M ✓
Gate 2 — Data Types

Do values match expected types — string, uint32, enumeration?

100M → valid string ✓
ios0 → valid string ✓
Gate 3 — Leafref

Does device "ios0" actually exist in /devices/device list?

ios0 → exists in CDB ✓

⚠ Failure examples: bandwidth=ABCDEF (wrong type) · device=ios99 (does not exist) · missing mandatory field → All abort with precise error. No device is ever touched.

Validation model: Service YANG constraints Failure: Transaction aborted, error returned to user
Step 05

Candidate CDB Write — Temporary Staging Store

Service YANG

What Happens

After all three validation gates pass, the service data is written into NSO's Candidate CDB (Configuration Database) — a temporary, transactional staging area. The Running CDB (the live, committed state) remains completely unchanged. Rollback at this point is free: no device has been contacted, no configuration lock is held on any router.

📌 Why it matters: Think of Candidate CDB as a "shopping cart" — items are staged before checkout. If anything fails later, the cart is simply discarded. Running CDB = what's currently live on the network.

Example — What gets written

Candidate CDB entry created
/services/simple-service[name='test1']
device = ios0
bandwidth = 100M
Running CDB: unchanged
Candidate CDB: test1 staged
No device contacted yet
Storage: Candidate CDB (not Running CDB) Rollback cost: Zero — discard candidate
Phase 3
Service Orchestration
Steps 6 – 8 · NSO takes ownership of the transaction
Step 06

Service Manager — Transaction Ownership

NSO Orchestration

What Happens

NSO's Service Manager detects the Candidate CDB change and takes full ownership of the transaction. It manages the entire lifecycle: invoking create/modify/delete callbacks, coordinating multi-device operations, and gating the final two-phase commit. If anything fails from here forward, Service Manager triggers automatic rollback across all devices.

Example

Service Manager detects change
CDB change detected: test1 (simple-service)
Operation type: CREATE (new service)
Target devices: ios0
Rollback plan initialized
Trigger: Candidate CDB change detected Responsibility: Full transaction lifecycle
Step 07

Servicepoint Trigger — Bridge to Code

Service YANG

What Happens

The YANG annotation ncs:servicepoint simple-service; embedded in the Service YANG is the bridge between data model and execution logic. When the Service Manager processes the service instance, it fires this named servicepoint. NSO looks up which Python class is registered under that name.

📌 Analogy: The servicepoint is like a webhook name — "when data of type X appears, call handler Y." The YANG model declares it; Python implements it.

Example

YANG annotation fires servicepoint
ncs:servicepoint "simple-service";
↓
NSO fires: sp="simple-service"
Servicepoint name = "simple-service"
NSO looks up registered handler
Source: ncs:servicepoint annotation in Service YANG
Step 08

Servicepoint Lookup — Find the Python Handler

Application Registry

What Happens

NSO resolves the servicepoint name to a registered Python class in its application registry. Python classes register themselves at package load time using the decorator @ncs.application.Service(servicepoint='simple-service'). If no handler is found, the transaction fails.

Example

Registry lookup
Servicepoint: "simple-service"
→ Registered class: SimpleService
→ File: packages/simple/python/main.py
Handler found → proceed
Handler missing → transaction fails
Mechanism: Python @Service decorator at package load Failure: No handler registered → abort
Phase 4
Mapping & Logic Execution
Steps 9 – 12 · Business logic, vendor detection, template selection
Step 09

Mapping Logic Layer — Core Decision Engine

Business Logic

What Happens

This is the brain of the service. The mapping layer decouples what the engineer asked for (abstract service intent: "bandwidth=100M on ios0") from how that translates to actual device config (vendor-specific CLI or XML). It decides: which vendor logic applies, which template to use, and what runtime values to inject. All subsequent steps execute based on decisions made here.

📌 Key benefit: One service definition works across Cisco, Huawei, Juniper. The mapping layer absorbs all vendor differences — the engineer never needs to know which vendor's CLI syntax to use.

Example — Three decisions made

Decision 1: Which vendor? → query NED ID
Decision 2: Which template? → cisco.xml or huawei.xml?
Decision 3: What values? → convert 100M → 100000 kbps
Role: Decouple intent from device-specific implementation
Step 10

Python cb_create Callback — Read Parameters & Apply Business Logic

Service YANG

What Happens

The Python cb_create function is called with the service node as context. It reads service.device and service.bandwidth directly from the Candidate CDB, then applies business logic: unit conversion (100M → 100000 kbps), interface selection, policy naming, QoS class derivation.

Example — Business logic applied

Python reads service inputs
device = service.device # "ios0"
bw_raw = service.bandwidth # "100M"
bw_kbps = parse(bw_raw) # 100000
iface = "GigabitEthernet0/1"
100M converted to 100000 kbps for Cisco CLI
Interface auto-selected from inventory
Variables dict prepared for template
Input source: Service YANG-defined CDB node Output: Variables dict for template rendering
Step 11

Vendor Selection — Identify Target Device Type

NED YANG

What Happens

Python queries the device's NED ID from /devices/device[ios0]/device-type/cli/ned-id in the CDB. This string uniquely identifies the vendor, OS, and NED version. All downstream template selection and translation logic is driven by this single value.

Example — NED IDs and outcomes

cisco-ios-cli-6.x → use Cisco IOS template
cisco-iosxr-cli-7.x → use IOS-XR template
huawei-vrp-cli-5.x → use Huawei VRP template
unknown-ned → error: unsupported device
ios0 → ned-id: cisco-ios-cli-6.x ✓
Query path: NSO core tailf-ncs-devices YANG Drives: All downstream template and translation decisions
Step 12

Template Selection — Choose the Right Config Blueprint

NED YANG

What Happens

Based on the NED ID from Step 11, the appropriate XML template is selected from the package's templates/ directory. Templates contain YANG paths native to each vendor's NED (e.g., /ios:interface/GigabitEthernet). A service package may have one template per vendor, or one shared template with vendor-conditional blocks.

Example

Template folder structure
templates/
├── cisco-ios.xml ← selected for ios0
└── huawei-vrp.xml
NED ID = cisco-ios-cli-6.x → cisco-ios.xml selected
Template contains Cisco-specific YANG paths
Template paths: NED YANG vocabulary Selection driver: NED ID from Step 11
Phase 5
Configuration Generation
Steps 13 – 14 · Abstract intent → concrete config tree
Step 13

Template Execution — Inject Variables & Resolve Paths

NED YANG

What Happens

The selected XML template is executed: all variable placeholders are replaced with actual values (device name, bandwidth in kbps, interface IDs, policy names), YANG paths are validated against the NED YANG schema, and conditional blocks are evaluated. The output is a fully populated YANG configuration subtree — structurally valid, vendor-specific, but not yet compared to current state.

Example — Variables injected into template

Template before → after injection
<bandwidth>{bw_kbps}</bandwidth>
↓
<bandwidth>100000</bandwidth>
<interface>GigabitEthernet0/1</interface>
All {variables} replaced with real values
YANG paths validated against cisco-ios NED YANG
Validation: NED YANG schema Output: Populated YANG config subtree
Step 14

Intended Configuration — Full Desired State

NED YANG

What Happens

The complete desired state of the target device is produced — every configuration element the service requires. This is a YANG data tree, not device CLI yet. Critically, it has not been compared to what is already on the device. It represents pure intent: "here is everything this service needs to exist."

📌 Important: At this point NSO knows what we WANT — it does not yet know what ALREADY EXISTS on the device. That comparison happens next in FASTMAP (Step 15–17).

Example — Intended config tree

ios:interface GigabitEthernet0/1
ios:bandwidth 100000
ios:service-policy output POLICY-100M
ios:description "test1 managed by NSO"
Full YANG tree — not yet filtered or sent
No device contact has occurred
Format: NED YANG data tree (not CLI) Next: Compare vs. last committed state (FASTMAP)
Phase 6
FASTMAP Delta Computation
Steps 15 – 17 · Compute only what changed — zero-touch idempotency
Step 15

FASTMAP Engine — Compare New vs. Last Committed

NED YANG

What Happens

NSO's FASTMAP algorithm compares the newly generated intended configuration (Step 14) against a snapshot of the service's last committed configuration stored in CDB. This is a pure local comparison — no device polling is required. NSO already knows what was last pushed because it stored a snapshot at the previous commit.

📌 Key advantage: No CLI "show running-config" to the device. FASTMAP is entirely local — comparing two CDB snapshots. This makes NSO extremely scalable across thousands of devices.

Example — First-time provision vs. modify

First time: Previous snapshot = empty → everything is CREATE
Modify: bandwidth 50M→100M → only that line is MODIFY
Delete service: snapshot present → everything is DELETE
Algorithm: FASTMAP — local CDB diff, no device polling Compares: Two NED YANG config trees
Step 16

DIFF Calculation — CREATE / MODIFY / DELETE

NED YANG

What Happens

FASTMAP produces a precise three-way change set in a single deterministic pass. Every node in the NED YANG config tree is classified: new nodes are CREATE, changed values are MODIFY, nodes present in the snapshot but absent now are DELETE. This changeset is the only thing forwarded to the device.

Example — Changeset produced

CREATE: ios:description "test1 managed by NSO" (new)
MODIFY: ios:bandwidth 50000 → 100000 (changed)
DELETE: ios:rate-limit (existed before, removed now)
UNCHANGED: ios:interface name → silently skipped
Output: CREATE + MODIFY + DELETE operations on NED YANG nodes Pass count: Single deterministic pass
Step 17

Delta Configuration — Only Changes Go Forward

NED YANG

What Happens

Only the computed delta is passed forward. Configuration already present on the device that matches intended state is silently dropped. This guarantees idempotency: pushing the same service configuration twice produces exactly zero device changes on the second run — nothing is reapplied unnecessarily.

📌 Idempotency = safety: Operations teams can re-run provisioning scripts without fear of disrupting a device that is already correctly configured. NSO will detect "nothing changed" and send nothing.

Example — Idempotent re-provision

Run 1: 3 commands sent to ios0 (CREATE)
Run 2 (same inputs): delta = empty → 0 commands sent
Result: device state is identical, no disruption
Property: Idempotent — same input = zero change on second run Output: Filtered NED YANG delta tree

Southbound Execution
Steps 18 – 21 · Delta hits the real device
Step 18

Device Manager — Resolve Connection Parameters

NSO Core

What Happens

NSO's Device Manager retrieves the connection parameters for the target device (ios0) from /devices/device in the CDB: IP address, port, transport protocol (SSH/NETCONF), and credentials. It manages connection pooling and enforces execution timeouts.

Example

ios0:
address: 10.0.0.1
port: 22
protocol: SSH (CLI NED)
credentials: <from authgroup>
Connection reused from pool if available
Timeout enforced (default: 30s)
Source: NSO core device model (CDB) Protocol: SSH (CLI NED) / NETCONF / RESTCONF
Step 19

NED Translation — YANG Delta → Device Native Commands

NED YANG

What Happens

The Network Element Driver (NED) translates the abstract YANG delta tree into device-native protocol commands. For a CLI NED (Cisco IOS): SSH-delivered command lines. For NETCONF NEDs: XML-encoded RPC. For RESTCONF NEDs: HTTP PATCH/PUT/DELETE. Each NED is a driver built specifically for one vendor and OS version.

Example — Same YANG, different output per vendor

YANG node → CLI translation (Cisco IOS)
ios:interface GigabitEthernet0/1
ios:bandwidth 100000
↓ NED translates to CLI:
interface GigabitEthernet0/1
bandwidth 100000
Huawei VRP: interface GE0/0/1 / bandwidth 100000
NETCONF NED: XML RPC <edit-config>
This is where: NED YANG is most actively consumed Output: Device-native CLI / XML / HTTP
Step 20

Southbound Execution — Push Commands to Device

Transport Layer

What Happens

Translated commands are pushed to the physical network device over the appropriate transport. NSO waits for explicit device acknowledgment before proceeding. Any device-side error (invalid syntax, hardware failure, capacity limit) triggers full transaction rollback across all devices in the transaction.

Example — Acknowledgment types

CLI NED: Waits for device CLI prompt (no error in output)
NETCONF NED: Waits for <rpc-reply><ok/>
RESTCONF NED: Waits for HTTP 200/201/204
Any error → full rollback of all devices
Transports: SSH / NETCONF / RESTCONF Error handling: Full atomic rollback
Step 21

Device Configuration Applied — Confirmation Received

Device / Network

What Happens

The network device confirms the configuration is active. For multi-device services (e.g., an L3VPN spanning 10 PE routers), all target devices must confirm success. A partial failure on any single device causes NSO to roll back every device in the transaction — restoring previous state everywhere. There is no partial success.

📌 All-or-nothing: If 9 of 10 routers succeed and 1 fails, NSO rolls back all 9 as well. The network either fully implements the service or returns to its exact previous state.

Example — Multi-device scenario

ios0: config applied ✓
ios1: config applied ✓
ios2: error — interface down ✗
Result: ios0 + ios1 rolled back → all 3 at original state
Guarantee: Atomic across all devices Partial failure: Full rollback everywhere
Phase 8
Commit & Persistence
Step 22 · Seal the transaction — update Running CDB
Step 22

Two-Phase Commit — Candidate Promoted to Running CDB

Both Models

What Happens

NSO executes a two-phase commit. The Candidate CDB is atomically promoted to the Running CDB — this is now the official live state. FASTMAP stores a snapshot of the NED YANG config that was just pushed, so future modifications or deletions can be computed relative to this exact state. The transaction is sealed.

📌 Two models persisted: Service YANG data (test1, ios0, 100M) committed to Running CDB. NED YANG data (the full device config tree) stored as FASTMAP snapshot for future delta computation.

What gets written on commit
Running CDB (Service YANG):
/services/simple-service[name='test1'] → persisted
FASTMAP snapshot (NED YANG):
Full device config tree stored for next diff
Audit log: Transaction ID, timestamp, user, device
Rollback file: NSO can undo via rollback #N
✓ Commit complete. Service test1 is live on ios0.
Commit type: Atomic two-phase commit Persisted: Service YANG + NED YANG snapshot Future: All changes computed relative to this snapshot

Key Concepts — Management Glossary

📐

YANG Model

A schema language that precisely defines the structure, data types, and rules for network configuration — similar to a database schema. Service YANG defines what engineers can configure; NED YANG defines each device vendor's vocabulary.

🗃️

CDB (Configuration Database)

NSO's internal database. The Candidate CDB is a staging area (changes in progress). The Running CDB is the live, committed state. This separation enables atomic, rollback-safe operations.

⚡

FASTMAP

NSO's algorithm that computes only the difference between the new intended state and the last committed state — without querying the physical device. This makes NSO scalable to thousands of devices and guarantees idempotent provisioning.

🔌

NED (Network Element Driver)

A vendor-specific adapter that translates abstract YANG configuration into device-native commands (Cisco CLI, Huawei commands, NETCONF XML, RESTCONF HTTP). One NED per vendor/OS version.

🔁

Idempotency

A property where running the same operation multiple times produces the same result as running it once. NSO's FASTMAP guarantees this: re-provisioning an already-correct service sends zero commands to devices.

⚛️

Atomic Transaction

All-or-nothing execution. If a service must configure 10 routers and router 7 fails, NSO rolls back all 9 previously successful routers. The network either fully implements the service or returns to its exact original state.
